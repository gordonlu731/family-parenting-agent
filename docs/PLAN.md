# 家庭育儿智能体方案与开发计划

版本：v1.2 微信入口选择与小程序条件  
日期：2026年11月6日  
用途：供家庭评审和 Codex 开发交接。本文为原始开发计划；实现状态以STATUS.md为准，应用尚未上线。

最新核心场景与记录建议见 [CORE_SCENARIOS.md](CORE_SCENARIOS.md)，已确定事项见 [DECISIONS.md](DECISIONS.md)，可执行任务与顺序见 [ROADMAP.md](ROADMAP.md)。本原始方案是设计背景，不能用来判断功能已经完成或要求恢复手动部署；实现状态以STATUS.md为准。

## 1 目标与已确定的方向

为一个家庭、一个宝宝开发可持续使用的育儿助手。家长和其他照顾者分别对话，共用宝宝档案、菜单和实际进食记录。优先完成“制定菜单、记录实际进食、根据反馈调整”的日常流程。

已确定：使用 Codex 协助开发；家人主要使用微信；采用国内可接入的模型 API。第一版默认做适合手机的网页，将链接发到家庭微信群。微信承担链接分发入口，应用本身提供聊天和共享记录。国内普通网络和微信内置浏览器的可用性必须实测，不预先承诺。

新增方向：微信内方便使用是主要验收条件，后续增加语音聊天。初期验证录音与播放，随后分为“一句一答语音”和“连续实时语音”两个阶段实施。后台业务、共享数据与语音渠道解耦；不把完整语音功能混入文本版交付，也不等到语音阶段才发现终端不兼容。

开发工具与运行模型分开：Codex 用于编写、测试和维护代码；育儿应用运行时由后台调用国内模型，家人无需使用 Codex 或配置模型密钥。

## 2 第一版使用流程

1. 家长创建家庭，确认宝宝档案，通过单次有效的邀请链接添加照顾者。
2. 助手根据档案、家庭做饭条件和近期记录生成七天菜单草稿。家长发布后，全家看到同一份菜单。
3. 照顾者输入“今天午饭吃了半碗饭，牛肉没吃”，系统整理为私人草稿，明确核对后保存实际进食记录，显示记录结果和撤销入口。
4. 家人提问或要求替换菜品时，后台读取最新档案、当前菜单和相关进食记录，再向模型请求建议。
5. 修改菜单后保留版本和修改说明；所有人刷新或重新进入页面即可读取最新状态。

普通问答不自动写成事实。只有明确的记录意图才产生写入；时间、餐次或涉及人员不清时，先用一个简短问题核对。

| 饮食回顾 | 展示近七天已记录内容和可尝试的调整 | 不把未记录视为没吃；不凭记录诊断营养缺乏 |

## 4 页面与家人操作

底部保留三个主要入口：今日、记录、问助手。宝宝档案、家庭管理和周菜单通过清晰按钮进入。

- 今日：当前日期、当前菜单、今天已记录的餐次、换菜入口。
- 记录：一个输入框，示例“午饭吃了半碗饭”；提供餐次和日期补充项；保存后展示可撤销结果。
- 问助手：文字对话，提供“生成一周菜单”“换一道菜”“看看最近吃饭情况”等快捷问题。
- 档案与设置：由家长确认过敏、维护规则、管理家人、导出数据。

面向长辈优先采用大字号、大按钮、短句和少层级操作。保存和模型等待必须有明确状态；模型不可用时，查看菜单、表单记录和历史查询仍可使用。

## 5 建议技术方案

以下为默认实施选择，用于控制第一版复杂度；实施时验证依赖版本并锁定。

| 部分 | 默认选择 | 原因与限制 |
| --- | --- | --- |
| 手机网页 | React 加 TypeScript，Vite 构建静态资源 | 页面可定制；需要微信内置浏览器实测 |
| 后台 | Python FastAPI | 集中处理权限、数据、模型调用和记录规则 |
| 数据库 | SQLite，使用事务和数据库迁移 | 适用于第一版单实例、小家庭规模；不做多服务器共享数据库文件 |
| 模型 | 阿里云百炼普通按量 API，千问文本模型作为候选 | 模型 ID 可配置；通过真实样例比较后确定，不预设某一型号最优 |
| 部署 | Docker Compose；前端构建结果由后台提供；HTTPS 反向代理 | 减少常驻组件；数据库放持久化目录 |
| 源码 | 独立公开源码 Git 仓库 | 与量化项目代码和数据分开；具体仓库名在建仓时确定 |

模型只由后台调用，密钥不进入浏览器、源码、截图或普通日志。使用实际业务可用的模型 API，不把编程工具专用套餐当作本应用的运行额度。

先评估用户已有 ECS 的地域、剩余资源、现有服务和域名条件。符合条件才复用，并采用独立目录、容器、数据卷和资源限制。未评估前，不改量化项目配置，不新增付费云资源。生产访问条件、域名相关要求和证书配置在部署阶段核实。

第一版采用单应用实例，控制 SQLite 写入事务时长。使用 SQLite Online Backup API 生成一致性备份，不直接复制正在写入的主数据库文件。并发写入或规模增长后再评估 PostgreSQL。

## 6 智能体如何工作

采用一个对话助手配合受限后台工具，第一版无需引入多智能体系统或复杂编排平台。

一次请求按以下步骤处理：

1. 后台确认当前成员与家庭权限，确定服务端 family_id 和 child_id。
2. 读取最新档案、已发布菜单、相关进食记录及必要的对话上下文。
3. 模型判断是问答、记录、菜单生成还是替换请求，并输出结构化结果或受限工具请求。
4. 后台校验字段、时间、家庭权限、已确认过敏和版本，再执行允许的操作。
5. 只有数据库提交成功才返回“已保存”；工具执行失败时明确说明未保存。

首批工具：读取档案、查询菜单、查询进食记录、新增或更正进食记录、保存菜单草稿、生成采购清单。发布周菜单、变更已确认过敏等操作通过明确界面确认。

不允许模型执行任意 SQL、任意 HTTP 请求或服务器命令。模型输出视为待校验数据；数据库权限与食品限制由后台执行，不能仅靠提示词。

## 7 数据与修改规则

主要数据实体：家庭、成员与角色、宝宝档案、进食事件、菜单版本、会话与消息、修改记录。档案中带来源和确认日期，进食事件保留原话、事件时间和录入时间。

- 所有业务记录绑定家庭及宝宝。每个读写接口都校验成员关系，不能接受模型自由指定家庭。
- 邀请令牌随机生成、服务端仅存哈希、可过期和撤销。兑换后建立成员会话；会话通过 HttpOnly、Secure Cookie 维护，并保护写入接口。
- 时间以 Asia/Shanghai 展示；“今天午饭”等相对表述以消息发送时间解析；跨日补记允许修改日期。
- 客户端重试使用幂等键。同一请求不重复入库；不同家人描述相似的一餐提示合并或核对，不擅自删除记录。
- 更新使用版本检查。发生冲突时保留最新数据并提示，不能静默覆盖。
- 记录“吃了多少”与计划份量分开。没有说明的量记为未知；“不喜欢”与“过敏”分开。
- 家人个人对话默认仅本人可见；从对话明确保存的宝宝记录和菜单供家庭共享。试用前清楚展示此规则。
- 撤销或更正记录保留修改来源。管理员可以导出和删除家庭资料；备份保留及删除规则在上线时说明。

## 8 菜单和育儿回答规则

菜单必须参考：已确认月龄、过敏状态、食材接受程度、做饭人可投入时间、可用食材、近期已记录饮食。

- 过敏状态设为“未知”“家长确认暂无已知过敏”“已知过敏”三种，不能把空白视为不过敏。生成个性化菜单前完成确认。
- 已确认过敏是硬限制；菜名、配料、替代品都要校验，模糊食材或配方先询问。
- 关注食物的形状、质地和处理方式。把有来源的食品安全规则落实到配方提示中；规则存在疑问时不标为已通过。
- 偏好依据多次实际反馈逐步调整；单次拒绝不永久排除，不因一顿吃少就要求下一顿强行补吃。
- 奶和补充剂作为家长报告资料记录，不自动更改剂量，不从短期饮食记录推断缺乏症或疾病。
- 一般育儿对话可提供解释、列出需补充的信息；遇到医疗问题区分日常建议与需要专业评估的情况，避免擅自诊断或给药。
- 第一版使用整理好的少量可追溯规则和配方资料。涉及本地饮食习惯或医疗规则时核实适用地区；不直接照搬国外地区专属例外。

## 10 必须通过的验收案例

1. 两位家人分别登录；一人记录午饭，另一人能查询到；未授权访问者读不到任何家庭内容。
2. 输入“午饭吃了半碗饭，牛肉没吃”，准确保存两项事实，不凭空换算克数。
3. 发送相同请求两次不会新增两条记录；两位家人记录疑似同一餐时提示核对。
4. 说“昨天那条记错了”时先定位确认，不删除或修改错误的日期。
5. 菜单包含明确做法、替换建议和食材；替换晚餐保留其他餐次及其他人的修改。
6. 测试过敏食材及其常见配料表达；不能通过改名、换菜或对话指令绕过限制。
7. 模型超时、限流或结果格式错误时不报“已保存”；表单记录和已有菜单可继续使用。
8. 清除浏览器缓存并重新登录后数据仍在；容器重启后数据仍在。
9. 用备份恢复到隔离测试环境，核对记录数量和菜单版本。
10. 微信内置浏览器及普通手机浏览器可登录、输入、保存和重新访问；在家人的实际国内网络验证。

真实模型另用约 20 条家庭场景测试抽取准确性、菜单约束、工具调用和失败处理。关键权限与过敏限制用确定性程序测试；真实模型用例记录结果，不能把模型评测当作安全权限的唯一证据。

## 11 费用与维护

费用分开核算：Codex 开发使用、模型 API 日常使用、云端运行及域名备份等支出。现有开发订阅不视为应用免费运行额度。

开发阶段先用模拟数据和模拟模型；真实模型接入后记录 token 使用量、调用次数和按当前费率估算的支出。配置请求长度、超时、工具轮次和每成员频率上限；每日或月度应用预算可设置，达到阈值后暂停新增 AI 调用，保留普通记录功能。应用估算可能与供应商账单有延迟差异，不能作为绝对账单封顶保证。

计划实现每日一致性备份，建议初始保留七份日备份和四份周备份，并保存一份独立于应用服务器的加密副本。最终备份位置和预算在部署时确定。升级前备份，发布保留可回滚镜像；不自动实施破坏性数据库变更。

## 12 上线前需要补齐的信息

不影响先开发页面与共享记录：

- 当前月龄或出生年月、已知食物过敏、明确饮食禁忌。
- 平日谁做饭、每餐可投入时间、常用食材和菜单偏好。
- 家庭成员昵称及管理员人选，无需收集身份证等无关资料。
- 可用模型账号和安全注入密钥的方法，不在普通聊天中明文传密钥。
- ECS 的地域、系统、剩余资源、已有服务、域名和访问条件；是否提供受限的部署访问。

真实家庭档案仅在私密部署中由家长确认和录入；公开源码及文档不包含家庭饮食、健康或成长历史，演示仅使用虚构数据。

## 13 给 Codex 的执行交接

请基于本文开发家庭育儿智能体。默认一个家庭、一个宝宝，家长和照顾者分别登录，共享档案、菜单和实际进食记录。先按阶段 A、B 完成可评审页面和真实持久化的家庭共享功能，再按 C 接入国内模型。不得把浏览器 localStorage 当共享数据库，不得把模拟回复当真实 AI，不得在数据库写入失败时显示已保存。

采用 React/TypeScript/Vite 前端、FastAPI 后台、SQLite 单实例和 Docker 部署。先读取目标仓库的现有约定，选择当前兼容依赖并锁定；若现有项目约束要求调整技术栈，说明原因后保持功能与验收目标。

身份鉴别、家庭权限、幂等和版本检查由后台执行；工具采用白名单；模型没有任意 SQL 和服务器执行权限。密钥仅在服务端安全配置。运行模型、base URL 和模型 ID 可配置。模型调用最小化传输个人信息，保留必要使用量指标并避免正文日志泄露。

微信便利性及后续语音是明确需求。阶段 A 先用隔离页面测试实际手机的 HTTPS 麦克风授权、录音和播放，完成结果记录。文字和语音必须调用同一个已鉴权业务服务，共用家庭资料与记录；按第14节保留会话、转写、音频输入输出适配接口，避免重复实现数据和权限。后续连续对话另立里程碑，不能把输入法转文字演示成已完成语音聊天。

按本文验收案例验证并记录未完成项。先用演示数据完成独立工作，遇到缺少密钥或部署权限时继续其他不依赖部分；不要要求用户逐条手工搭建项目。未明确确认前不更改量化项目、不创建付费云资源、不公开家庭数据；源码仓库按维护者后续明确选择设为Public。应用上线前验证实际国内网络与微信兼容性。

## 14 微信使用与语音扩展

### 家人如何方便进入

第一版入口仍为家庭微信群中的网页链接，可配合微信收藏等方式重复进入。首次邀请建立各自身份；后续在会话有效期内保留登录，权限撤销后失效。界面按“点开、点说话或输入、看到结果”设计，保留文字、语音和表单降级入口。

不默认要求微信公众号、微信登录或微信 JS-SDK。若浏览器原生录音在实际设备上不满足要求，再评估微信 JS-SDK 或小程序方案及其账号、域名、审核和权限条件；不预先承诺所有个人账号都能启用全部能力。不向用户提供绕过平台限制的方案。

### 入口形式与选择条件

| 形式 | 家人如何使用 | 适用情况 | 需要先确认 |
| --- | --- | --- | --- |
| 微信网页 H5 | 家庭群链接打开，可收藏；在页面里看菜单、记录和对话 | 当前个人家庭版本默认入口 | 实际网络、登录保持、录音播放和 HTTPS |
| 微信小程序 | 通过小程序入口进入，同一家庭成员各自查看和记录 | 有合适主体与发布条件后，评估作为长期入口 | AI 问答类目、主体、审核资料及所需音频能力 |
| 微信公众号对话 | 家人关注账号后分别发消息，后台读取同一家庭资料 | 偏重消息问答，菜单页面可另设入口 | 账号和接口权限、消息形式、回复能力及审核要求 |

“全家一起用”默认指分别登录、共享宝宝档案和实际进食记录；不要求全家同时加入一场语音通话，不默认共享全部私人对话。微信群只负责分发入口，不能由群成员身份自动推导应用内家庭访问权限。

截至本版查询，腾讯云开发官方《微信云开发在用证明》明确：深度合成类目仅向非个人主体开放，个人主体小程序无法申请该类目，AI 问答属于其子类目之一。因此，不能把“个人注册小程序后即可正式发布 AI 问答”作为本项目既定前提。具体发布资格须在拟用主体及微信公众平台核实；该判断不是对所有普通小程序功能的限制，也不是网页可不核实其适用要求的结论。

实时音频权限还需按具体链路核实。腾讯 TRTC 小程序方案中，live-pusher/live-player 推拉流组件要求企业类主体及支持的类目；这一限制仅说明该技术路线的条件，不能推导普通录音、一句一答或所有其他音频实现都采用相同条件。先选适合本项目的交互，再核实权限，不盲目购买 RTC 服务。

默认执行次序保持为：个人家庭网页试用、验证语音体验、核实小程序主体与类目、再决定是否新增小程序客户端。若用户已有合适非个人主体并明确优先小程序，可在早期核实资格后调整客户端开发顺序。新增小程序时复用后台业务和数据库，按官方登录流程把小程序身份绑定到同一应用成员；网页会话 Cookie 不能直接当作小程序登录方案，不能仅通过昵称关联身份。

### 语音按阶段实施

| 阶段 | 使用体验 | 技术方向 | 交付边界 |
| --- | --- | --- | --- |
| 早期兼容性验证 | 点击开始录音、停止、播放测试音频 | HTTPS 网页，权限检测、可用音频格式与播放验证 | 仅测试终端能力，未接智能体，不作为语音功能上线 |
| 一句一答 | 用户说一句，显示转写，助手回答并可播报 | 录音或分段流式语音识别，加现有智能体，加语音合成 | 不承诺同时听说、自然打断或后台持续通话 |
| 连续实时对话 | 点开始对话后可连续交流，显示字幕，可结束及打断 | 实时语音模型与工具调用，或流式识别加文本智能体加流式合成 | 通过工具调用、回声、弱网与权限测试后才启用 |

国内实时语音服务已有 WebSocket、WebRTC 等接入方式，最终选择以模型能力和实际手机测试为准。不能假设当前文本模型的 API 直接接收音频；语音识别、语音合成、端到端实时对话可能涉及不同接口、权限和计费。

### 从文字阶段保留的架构

- 前端区分文本输入、音频输入、字幕和音频播放；业务消息保留稳定的消息 ID、会话 ID 和输入类型。
- 后台统一提供已鉴权的家庭资料与记录工具。后续实时模型的工具请求也由后台校验权限、过敏和版本后执行，不因语音接入绕过校验。
- 长期 API Key 只在后台保存；若采用浏览器到供应商的连接，只使用供应商支持的短期凭证，并验证工具链路仍受后台控制。
- 菜单和记录的事实只来源于成功提交的数据。实时语音仅在收到工具成功结果后播报“已记录”。
- 用户打断时停止旧语音播放和相关生成；停止播报不自动撤销已完成的数据写入，撤销必须走业务工具。
- 语音模型可更换，既有家庭数据库、历史记录和核心业务接口继续使用。若后续改小程序，主要新增或调整客户端与接入层，不保证网页界面代码原样复用。

### 语音验收与费用

至少覆盖家人实际 Android 手机；有 iPhone 使用者时加入 iOS 微信。验证录音授权、拒绝授权、首次播放、连续使用、回声、普通话口音、常见食材词、日期和数量、弱网与断线、来电以及切后台后恢复。不要把开发电脑正常运行视为微信端验收通过。

识别不清时显示转写并允许纠正。过敏、药名、剂量、数量等关键信息识别存在歧义时先核对；不凭语音置信度猜测重要事实。身份以当前登录成员为准，不用声纹识别代替权限判断。

默认明确点击后才打开麦克风，提供显眼的收音状态和结束按钮。离开页面、结束或断线后停止录音和相关连接；不承诺锁屏及后台持续对话。原始录音默认只作临时处理并及时清理，保留必要文字记录，任何长期录音保存需明确说明与用户选择。

语音单独统计识别、合成、实时会话时长及费用；设置单次会话时长和并发上限。费用阈值触发时结束音频会话并回退文字；具体价格在选型时核实，不假定包含在文本 API 或 Codex 开发额度内。

如果微信网页上的语音体验不稳定，再评估原生小程序。评估依据是家人的实际手机测试及所需语音体验，不在兼容性未知时直接开展第二套客户端开发。
