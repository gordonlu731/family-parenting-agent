# 食材、推荐资料与采购数据规则

应用0.3.0，2026年11月8日。此文描述已实现行为，不能替代真实模型及终端验收。

## 共享食材

- `GET /api/pantry`返回家庭修订号、最多200条原料/熟食/用完记录及确认新旧提示。无跨家庭访问，响应不缓存。
- `PUT /api/pantry`接受当前修订号、1–20项变更及明确review_confirmed；每项有名称、位置、类型、状态、可选数量/单位及粗略说明。更新已有项须带原id/version，新项version为0。
- 数量为家中当前总量，不是采购增量。数字量支持克、毫升、个、份；未知量使用null与适量，粗略余量留在amount_note；不强制称重。
- 名称仅做Unicode NFKC、大小写与空白规范化，不自行猜同义词。一个家庭内同名+同位置+同生熟类型只有一项；已有项应更正或恢复，不重复累加。
- 写入使用BEGIN IMMEDIATE、家庭修订及行版本、幂等键和审计。整批任何冲突都回滚；成员停用后不得写入。
- 用完时清除可用量，记录仍可通过更正恢复；误建记录可标为无效/用完。不是永久删除或数据隐私删除功能。
- 写入成功由服务端记录确认时间和更新人。默认7天需重确认，可配置PANTRY_RECONFIRM_DAYS（1–30）；不是食品保质期，不推断是否能吃。

## 自然语言确认

`POST /api/pantry-proposals`只处理当前库存；计划和不明表达先追问，名称与证据必须来自原话。模型不获得家庭成员ID、登录凭证或库存数据库ID。现有项关联由服务端按名称/位置/类型查找；同名多个位置未说明时追问。

数字量缺少原话支持时降为未知，并保留原话说明。草稿可更正，私有、24小时有效；经既有proposal编辑/确认接口保存，确认时检查库存修订。只生成草稿不改变共享库存。进食、菜单和食材三类写入互相独立；混合一句的多类写入尚未实现。

## 推荐资料

菜单与只读问答使用近七天已确认实际记录、已存菜单和可用原料。参考库存排除熟食、用完和待重确认；数量未知仍可作为“有这种原料”的资料，不能视为够用。

最多14条实际记录、15餐历史菜单、40项原料，并限制资料序列化长度；显示总量、纳入量、节选状态和日期。单条内容也可能截短。历史菜单是当前保存版本，不能宣称当时实际吃了或是完整版本时间线。

提供给模型的是不含身份/数据库ID的R/M/P临时资料编号。模型basis只能引用当前提供的编号；编号存在不证明推理正确。草稿保留资料快照供核对。只读问答另提供有界的当前/未来菜单。

发布时仍检查已确认档案、目标餐版本和库存修订；原料随时间进入待确认也会阻止旧草稿发布。历史反馈的更正在下次读取/生成时生效；已发布菜单不会自动因新反馈重写。

## 采购缺口

1. 只读已发布菜单，按规范化名称和单位先合并全部需求；手工菜单无结构化数量时保留未知。
2. 对同名同单位、近期确认、数字量已知的原料汇总，针对合并需求仅抵扣一次。
3. 已知库存能覆盖明确用量时为enough；明确有缺口时为need_buy；未知需求、余量不清、记录陈旧或单位不能匹配时为check。没有库存记录只表示清单未登记，界面仍提示按实际核对。
4. 不同单位不换算；“份”因规格不明列待核对；熟食不作原料抵扣；不把同义词猜测当确定匹配。同一种食材有额外未知用量时，不宣称整体足够。
5. 读取不写库存。换菜后实时重算；买好后确认当前总量或用完状态，再刷新缺口。独立的共享采购数量覆盖单尚未实现，可通过更正库存或菜单重算。

## 数据升级与恢复

003新增pantry、pantry_revisions及proposals.context_snapshot，保留既有表数据。旧草稿的快照默认为空；新草稿有新校验。不要改001/002或删除持久卷来升级。上线升级前使用SQLite Online Backup API创建一致性备份，先在隔离目录验证迁移、完整性和恢复。单元集成验证使用虚构旧库，不表示生产恢复已演练。
