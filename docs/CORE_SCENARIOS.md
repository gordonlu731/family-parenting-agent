# 核心需求场景与记录信息（2026年11月8日）

目标：结合历史菜单、宝宝实际进食和接受情况、家里现有食材及当前家庭条件，推荐可调整的菜单，帮助按缺口买菜，再将实际反馈用于下次推荐。需求梳理先于继续扩充功能；本稿不表示功能已实现。

日常闭环来自用户明确提出的核心需求。下方“补充记录建议”来自产品设计讨论，尚未逐项确认或实现；不要将全表变成必填项。当前能力见STATUS.md，执行任务见ROADMAP.md。

## 日常闭环

1. 回看：按日/周查看过去安排过什么、实际吃过什么、接受情况和备注；区分计划、已做、实际吃了、未记录。回顾结果用于下一轮推荐。
2. 现有食材：全家共享有哪些食材、是否还有、粗略余量和确认时间；不要求称重或维护复杂进销存。支持一句话新增、用完、更正。这里的剩菜优先指剩余食材，熟菜须另行标注，不直接套用原料推荐逻辑。
3. 推荐菜单：读取已确认档案、历史菜单、实际反馈、现有食材、做饭时间及这次要求，建议下一餐或未来几天的菜。说明推荐理由、所用现有食材、还缺什么；可从历史好评菜中复用，兼顾适当变化。一次拒吃不自动永久排除食材。
4. 调整确认：按餐换菜、换食材或缩短做饭时间；保留未改餐次。草稿确认后才成为全家共用计划；调整后重算采购缺口。
5. 买菜去重：从确认后的菜单汇总食材，与可用余量比对，分为需要买、家里足够、已有但数量待确认。不同单位不强行换算；仅知道名称不自动认定够用。用户可以更正清单。买完后可用简单勾选或一句话确认更新现有食材，不要求独立采购流水账。
6. 实际反馈：家人记录真实吃了什么、粗略份量、接受情况及必要备注，也支持实际与计划不同、补记和更正；不把菜单发布自动视为已做或已吃。反馈成为后续推荐依据。

## 回看与推荐如何配合

回看提供可核对的事实和记录覆盖情况，例如最近安排了哪些菜、哪些实际吃了、哪些多次拒吃、哪几天未记录。推荐引用这些事实并结合当前食材和要求提出新菜单；显示依据与不确定项，而不是仅给一张历史统计页。未记录不等于没吃，已安排不等于已经吃过。

## 简化库存操作

第一版以食材名称、可选粗略余量、存放位置和最后确认时间为主。日常可说“还有两个番茄，牛肉用完了”，助手先整理再确认共享更新。发布菜单不扣库存；记录宝宝吃了某菜也不自动按配方精确扣减，因为实际用量和全家用量未必已知。库存陈旧或量不明时先提示确认，不静默抵扣采购。

## 补充记录建议：以改善推荐为目的

| 信息 | 建议记录方式 | 更新频率与用途 | 当前实现 |
| --- | --- | --- | --- |
| 宝宝基础与已确认限制 | 月龄、已确认过敏、接受的质地/处理方式；出生日期可作为自动计算月龄的可选设计 | 初始核对、变化时更新；不从旧聊天自动导入真实档案 | 月龄、过敏、喜好、备注已有；出生日期和独立质地字段未实现 |

| 粗略份量与接受情况 | 半碗、几口、没吃或未说明；不要求克重/热量 | 每餐按已知情况填写；“没吃”不必然代表“不喜欢” | amount及acceptance已有；新量表需兼容历史记录 |
| 做法与质地反馈 | 虚构例：“肉丸接受，肉片没吃” | 有差异时补充；积累食材+做法反馈，避免永久排除食材 | 可记备注；独立字段和汇总未实现 |
| 临时情况 | 胃口、餐前奶或零食、身体状态等，仅记家人观察 | 有变化或影响理解时补充；不自动推断原因或诊断 | 可记备注；没有专门健康事件模型 |
| 进食后异常反应 | 发生时间、食物、观察到的表现；与确诊过敏分开 | 有情况时记录；模型不得自动写成确诊过敏 | 可记备注；独立事件及归因未实现 |
| 家庭做饭条件 | 用餐人数、宝宝单做/全家同做、设备与时间 | 初始设置、变化时改；影响难度和采购量 | 做饭时间和备注已有；其他独立字段未实现 |
| 食材现状 | 名称、粗略余量、位置、最后确认；购买/开封时间可选 | 买入、用完、记错时更新；可食用状态由家人核实 | 共享食材已有表单与自然语言草稿，保存当前总量/粗略说明、位置、生熟、用完和确认时间 |
| 调整原因与烹饪反馈 | 没食材、太费时、换口味、容易做等 | 换菜或做完顺手选/说；改善后续推荐 | 可在替换说明填写；原因分类或统计未实现 |

最小操作建议：正常一餐只需核对“实际食物、粗略份量/接受情况、特别备注”；记录人和录入时间由服务端填写。菜单可减少重复输入，但必须明确确认实际情况。睡眠、排便、活动、身高体重等保留按需记录的讨论空间，不作为菜单流程每日必填项。

一句话可能包含多个意图。虚构输入“中午肉丸吃了几口，胡萝卜没吃，冰箱胡萝卜还剩一点”，应整理为进食草稿和库存变更，分别清楚展示确认结果。部分失败不能声称全都保存；误识别可更正，不明信息先核对。此混合意图能力尚未实现。

## 回看必须回答的问题

- 最近安排过什么，实际记录吃过什么，哪些日期/餐次资料不完整？
- 哪些菜在多次记录中接受较好，是否与做法有关？单次拒绝不等于稳定偏好。
- 哪些菜单经常被换掉，已记录的原因是什么？原因未知就保留未知。
- 现有且经过确认的食材能用于哪些菜，还缺哪些？余量与更新时间不明时提示核对。

推荐应引用可核对的日期、菜单或实际反馈，说明历史覆盖范围和未知项。记录更正后使用当前有效内容并保留修改追溯。

## 优先级与验收

P0：历史计划/实际回看、共享现有食材、结合历史和食材推荐、单餐调整、采购缺口去重、实际反馈记录，形成完整闭环。

P1：临近使用需求的食材排序、家常菜收藏、常见替换方案、家庭做饭偏好。存放和可食用状态由家长确认，不能仅按购买日期宣称食品安全。

后续：语音、小程序、识图和外部采购服务；不阻塞第一版日常闭环。

验收示例（虚构）：家人确认家里有两个番茄和部分牛肉。助手依据近期菜单与反馈推荐三天菜品，标明使用现有食材和推荐理由。确认菜单后清单只列确实需要买的食材，牛肉余量不明时列为待确认。换掉某餐后清单同步更新。实际进食记录显示宝宝吃了什么，下轮推荐可引用该记录；不能把所有计划自动计入吃过的历史。
