# 核心需求场景（需求梳理稿，2026年11月8日）

目标：结合历史菜单、宝宝实际进食和接受情况、家里现有食材及当前家庭条件，推荐可调整的菜单，帮助按缺口买菜，再将实际反馈用于下次推荐。需求梳理先于继续扩充功能；本稿不表示功能已实现。

## 日常闭环

1. 回看：按日/周查看过去安排过什么、实际吃过什么、接受情况和备注；区分计划、已做、实际吃了、未记录。回顾结果用于下一轮推荐。
2. 现有食材：全家共享有哪些食材、是否还有、粗略余量和确认时间；不要求称重或维护复杂进销存。支持一句话新增、用完、更正。这里的剩菜优先指剩余食材，熟菜须另行标注，不直接套用原料推荐逻辑。
3. 推荐菜单：读取已确认档案、历史菜单、实际反馈、现有食材、做饭时间及这次要求，建议下一餐或未来几天的菜。说明推荐理由、所用现有食材、还缺什么；可从历史好评菜中复用，兼顾适当变化。一次拒吃不自动永久排除食材。
4. 调整确认：按餐换菜、换食材或缩短做饭时间；保留未改餐次。草稿确认后才成为全家共用计划；调整后重算采购缺口。
5. 买菜去重：从确认后的菜单汇总食材，与可用余量比对，分为需要买、家里足够、已有但数量待确认。不同单位不强行换算；仅知道名称不自动认定够用。用户可以更正清单。买完后可用简单勾选或一句话确认更新现有食材，不要求独立采购流水账。
6. 实际反馈：家人记录真实吃了什么、粗略份量、接受情况及必要备注，也支持实际与计划不同、补记和更正；不把菜单发布自动视为已做或已吃。反馈成为后续推荐依据。

## 回看与推荐如何配合

回看提供可核对的事实和记录覆盖情况，例如最近安排了哪些菜、哪些实际吃了、哪些多次拒吃、哪几天未记录。推荐引用这些事实并结合当前食材和要求提出新菜单；显示依据与不确定项，而不是仅给一张历史统计页。未记录不等于没吃，已安排不等于已经吃过。

## 简化库存操作

第一版以食材名称、可选粗略余量、存放位置和最后确认时间为主。日常可说“还有两个番茄，牛肉用完了”，助手先整理再确认共享更新。发布菜单不扣库存；记录宝宝吃了某菜也不自动按配方精确扣减，因为实际用量和全家用量未必已知。库存陈旧或量不明时先提示确认，不静默抵扣采购。

## 优先级与验收

P0：历史计划/实际回看、共享现有食材、结合历史和食材推荐、单餐调整、采购缺口去重、实际反馈记录，形成完整闭环。

P1：临近使用需求的食材排序、家常菜收藏、常见替换方案、家庭做饭偏好。存放和可食用状态由家长确认，不能仅按购买日期宣称食品安全。

后续：语音、小程序、识图和外部采购服务；不阻塞第一版日常闭环。

验收示例（虚构）：家人确认家里有两个番茄和部分牛肉。助手依据近期菜单与反馈推荐三天菜品，标明使用现有食材和推荐理由。确认菜单后清单只列确实需要买的食材，牛肉余量不明时列为待确认。换掉某餐后清单同步更新。实际进食记录显示宝宝吃了什么，下轮推荐可引用该记录；不能把所有计划自动计入吃过的历史。

## 当前实现与缺口

0.2.3已有共享档案/实际记录、菜单草稿与确认、单餐替换及基础采购汇总。现有食材目前只作为生成时的临时输入，还没有持久共享的库存；采购汇总还没有减去家里现有食材。历史菜单、实际反馈和现有食材的联合推荐及专门回顾页面尚未完整打通。真实模型、微信和浏览器验收仍待完成。
